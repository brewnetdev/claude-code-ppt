01effort 레벨을 전부 검토하라

증상 — effort 선택 기준이 없다 / 비용·지연시간이 과하다

effort(추론 노력 수준)는 Fable 5.1에서 지능·지연시간·비용을 맞바꾸는 주 제어 장치입니다. 기본값 high에서 시작해 low · medium · xhigh · max를 자신의 평가셋(eval)으로 직접 스윕하십시오.

가장 흔한 실수

Fable 5에서 이미 스윕을 돌렸더라도 다시 돌려야 합니다. effort 레벨 이름은 모델 간에 동일한 사고량을 뜻하지 않습니다. "우린 5에서 medium이 최적이었으니 5.1도 medium" 은 근거 없는 이월입니다.

5.1에서의 레벨별 특징

  • 전 구간 향상: Fable 5 대비 성능 향상이 모든 effort 레벨에서 나타나며, 상위 레벨에서 격차가 가장 큽니다.
  • medium: 대략 Fable 5 수준의 결과를 더 낮은 비용으로 냅니다. 평가셋에서 품질이 유지된다면 medium이나 low로 내리는 것이 정답입니다.
  • low: 작업당 비용 면에서 Opus·Sonnet 계열과 경쟁하면서 점수는 더 높은 경우가 많습니다. "작은 모델을 높은 effort로 돌리려던 자리"에 Fable 5.1 low를 후보로 넣으십시오. 이것이 이 절에서 가장 실무적으로 값나가는 한 줄입니다.

02사용자에게 보이는 진행 보고 요청

증상 — 툴 호출 사이에 사용자용 텍스트가 거의 없다

Fable 5.1은 긴 툴 호출 턴 중에 사용자에게 보이는 업데이트를 Fable 5보다 적게 씁니다. effort가 높고 툴 체인이 길수록 더 심해집니다. 결과적으로 사용자는 몇 분간 침묵을 보거나, 전체 작업이 아니라 마지막 단계만 요약한 최종 메시지를 받습니다.

1단계 — 그 업데이트가 클라이언트에 도달은 하는지 확인

"방금 뭘 찾았고 다음에 뭘 할지" 같은 짧은 메모는 진행 업데이트 thinking 블록으로 돌아옵니다. 그런데 thinking.display의 기본값이 "omitted"(생략)이면 이 블록들이 비어서 옵니다. 즉 모델은 말했는데 여러분의 앱이 안 받고 있는 상태일 수 있습니다.

  • display: "updates" 설정 (베타 헤더 thinking-display-updates-2026-08-18) → 비어 있지 않은 thinking 블록을 상태 표시줄 한 줄씩 렌더링
  • display: "summarized" 설정 → 요약된 추론과 함께 수신

2단계 — 서술을 억제하는 기존 프롬프트 제거

이전 세대 모델은 오히려 업데이트를 과하게 내보내서, 많은 팀이 시스템 프롬프트에 hold all findings for the final response("모든 발견은 최종 응답까지 보류") 같은 줄을 넣어두었습니다. 새 지시를 추가하기 전에 이런 줄부터 지우십시오. 억제 지시를 남긴 채 촉진 지시를 얹으면 서로 상쇄됩니다.

3단계 — 그래도 부족하면 짧게 지시

시스템 프롬프트 추가 (원문 그대로 사용)

Before you start, say in a line what you're about to do; brief updates while you work help the user follow along. Close with a short recap that stands on its own — what you found, what you did, and what's next — so a reader who only sees the last message has the full picture.

해설: 시작 전 한 줄 예고 → 작업 중 짧은 업데이트 → 마지막 메시지만 봐도 전체 그림이 서는 자립형 정리로 마감. 세 번째 조건이 핵심입니다. 페어 프로그래밍처럼 사람이 옆에서 지켜보는(human-in-the-loop) 상황에서 특히 유용합니다.

UI가 툴 출력을 숨긴다면 반드시 알려줄 것

제품이 터미널 출력을 접거나 감추는 구조라면, 모델은 "사용자에게 보여주려고" 명령을 실행하는데 정작 UI는 그걸 표시하지 않는 헛수고가 발생합니다. 이 사실을 턴 범위 시스템 메시지(clear_at: "next_user_message", 베타)로 전달하십시오.

Only you see that command's output — the user's terminal shows at most a few lines of it. If the user needs to read any of it, put it in your reply.

해설: "그 명령의 출력은 너만 본다. 사용자 터미널엔 몇 줄밖에 안 나온다. 사용자가 읽어야 할 내용이면 네 답변 본문에 직접 넣어라."

03에이전트 루프의 툴 콜 묶어 보내기

증상 — 한 턴에 툴 호출을 하나씩만 한다

Fable 5.1은 보통 병렬 툴 호출을 잘합니다. 사용자가 "A와 B와 C를 가져와" 라고 명시하면 세 개를 병렬로 발행합니다. 문제는 다음 호출이 명시되지 않고 작업 흐름상 암묵적으로 도출되는 경우 — 커스텀 코딩 에이전트, bash+에디터 하네스, 컴퓨터 유즈 루프 — 여기서는 한 턴에 하나씩 나가는 경향이 있습니다.

답변 품질에는 영향이 없습니다. 하지만 매 여분의 턴마다 토큰 + 왕복 지연 + 실제 시간이 소모됩니다. 한 문장이면 교정됩니다.

현재 요청 끝에 덧붙이는 넛지 (원문 그대로)

First privately list what you need next; then request every item that doesn't depend on another's result in this one response.

해설: "먼저 다음에 필요한 것을 속으로 나열하라. 그다음 다른 것의 결과에 의존하지 않는 항목 전부를 이 한 번의 응답에서 요청하라." 의존성 유무를 판단 기준으로 명시한 것이 요점입니다.

어디에 넣을 것인가 — 이 부분이 진짜 함정

툴 결과를 되돌려 보낼 때마다, 그 user 메시지 뒤에 턴 범위 시스템 메시지로 새 복사본을 append합니다. messages 배열에 role: "system" + clear_at: "next_user_message" 항목을 넣는 방식입니다. 이후 user 메시지가 생기면 API가 이전 복사본들을 자동으로 비우므로, 모델은 가장 최신 하나만 읽습니다.

절대 하지 말 것

이전 복사본을 지우거나 고쳐 쓰지 마십시오. 배열에 그대로(byte-for-byte) 두면 됩니다. 비워진 뒤에는 모델이 보지 않고 입력 토큰도 소모하지 않습니다. 반대로 삭제·수정하는 순간 그것은 "이전 턴의 편집"이 되어 프롬프트 캐시가 그 지점부터 재시작되고, 그 뒤의 thinking 블록들이 무효화됩니다. (4절)

베타 헤더: mid-conversation-system-clear-at-2026-08-21. 베타를 쓰지 않는다면, 같은 user 메시지 안에서 tool_result 블록들 뒤에 텍스트 블록으로 이 문장을 넣으십시오.

루프 구조 (Python, 공식 예제 기준)

import anthropic

client = anthropic.Anthropic()

BATCH_NUDGE = (
    "First privately list what you need next; then request every item "
    "that doesn't depend on another's result in this one response."
)

messages = [
    {"role": "user", "content": "Summarize pyproject.toml and README.md."}
]

while True:
    response = client.beta.messages.create(
        model="claude-fable-5-1",
        max_tokens=16000,
        betas=["mid-conversation-system-clear-at-2026-08-21"],
        tools=tools,
        messages=messages,
    )
    # 어시스턴트 턴은 반환된 그대로 append (thinking 블록 포함)
    messages.append({"role": "assistant", "content": response.content})
    if response.stop_reason != "tool_use":
        break

    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            # ... 실제 툴 실행 후 tool_result 블록 구성
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": run_tool(block),
            })

    # user 턴에는 툴 결과만, 그 뒤에 넛지의 새 복사본을 턴 범위 시스템 메시지로.
    # 이전 복사본은 그대로 둔다 — API가 알아서 비운다.
    messages.append({"role": "user", "content": tool_results})
    messages.append(
        {"role": "system", "content": BATCH_NUDGE, "clear_at": "next_user_message"}
    )

04대화 히스토리는 추가 전용(append-only)

증상 — bound to a different conversation 오류 / 하네스가 이전 턴을 수정함

핵심 규칙 한 줄: 각 assistant 턴을 API가 반환한 그대로(thinking 블록 포함) 히스토리에 붙이고, 요청 사이에 이전 턴을 절대 편집하지 마십시오.

05글의 밀도 — 멋부린 문장 제거

증상 — 문장이 길고 문단 구분이 적어 빽빽하다

Fable 5.1의 글쓰기는 전반적으로 이전 세대보다 낫습니다. 상투어가 줄었고, 설명 없는 전문용어도 줄었습니다. 다만 일부 경우 Fable 5보다 산문 밀도가 높습니다. 문장이 길어지고 문단 나눔이 적어집니다.

해법은 "짧게 써라"가 아니라 안티패턴을 정의해주는 것입니다. 공식 권장은 mannered prose(멋부린 문장)라는 개념을 예시와 함께 정의하는 긴 블록입니다. user 메시지에 넣는 것이 선호되며, 시스템 프롬프트도 가능합니다.

전체판 (원문 그대로)

Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning." Instead of "this point still matters," they write "this point earns its keep." The phrases exist to display the writer, not to convey the idea, and readers can tell. That is why mannered prose irritates: it makes the reader work harder so the writer can perform. It is also imprecise. Metaphors drag in connotations the writer did not choose and cannot control. The fix is to say what you mean. When a literal phrase is available, use it.

해설: 멋부린 문장이란 직설적 진술 자리에 비유와 장식을 넣는 것입니다. "조정할 만한 파라미터"라고 하면 될 것을 "돌려볼 만한 다이얼"이라고 쓰는 식. 이런 표현은 아이디어를 전달하는 게 아니라 글쓴이를 전시하며, 독자는 그걸 알아챕니다. 게다가 부정확합니다. 비유는 글쓴이가 선택하지도 통제하지도 못한 함의를 끌고 들어옵니다. 해법은 뜻하는 바를 그대로 말하는 것. 직역 표현이 존재하면 그것을 쓸 것.

축약판 — 대개 이것만으로도 동작

Please remove all mannered prose.

이 지시는 anti-AI-slop 원칙의 텍스트 버전입니다. 시각 산출물에서 그라데이션·글로우를 금지하는 것과, 산문에서 비유·장식을 금지하는 것은 같은 규칙의 두 얼굴입니다. 강의 교안·블로그 초안 생성 시 이 한 줄을 상시 프롬프트에 고정해두면 결과물의 "AI 티"가 눈에 띄게 줄어듭니다.

증상 — 답변에 필요한 만큼의 구조가 없다

방향이 뒤집혔습니다. 이전 모델들은 채팅에서 불릿과 볼드를 과용했고, 그래서 많은 프롬프트에 그것을 억누르는 안티포맷팅 규칙이 들어 있습니다. Fable 5.1은 반대 방향입니다 — 볼드를 덜 쓰고, 제목·목록·따옴표에 손을 덜 뻗습니다.

따라서 기존 프롬프트의 안티포맷팅 문구를 찾아 제거하거나, "언제 어떤 포맷이 적절한지"를 규정하는 규칙으로 교체하십시오.

In conversational, personal, or emotional exchanges, keep to plain prose.

증상 — 일 끝나기 전에 턴 종료 / 이미 요청한 일에 다시 허가를 물음

Fable 5.1은 목표가 명확하면 방법론 지시가 거의 없어도 아주 긴 작업을 수행합니다. 문제는 복잡한 비동기 워크로드에서 나타납니다. 넛지가 없으면 모델이 다음을 합니다:

적용 지침

블록 1 — 자율 실행 선언

You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking 'Want me to…?' or 'Shall I…?' will block the work. For reversible actions that follow from the original request, proceed without asking. Stop only for destructive actions or genuine scope changes the user must decide. Offering follow-ups after the task is done is fine; asking permission before doing the work is not.

Exception: when the user is describing a problem, asking a question, or thinking out loud rather than requesting a change, the deliverable is your assessment. Report your findings and stop. Don't apply a fix until they ask for one.

Before ending your turn, check your last paragraph. If it is a plan, an analysis, a question, a list of next steps, or a promise about work you have not done ('I'll…', 'let me know when…'), do that work now with tool calls. That includes retrying after errors and gathering missing information yourself. Do not stop because the context or session is long. End your turn only when the task is complete or you are blocked on input only the user can provide.

Before running a command that changes system state (such as restarts, deletes, or config edits), check that the evidence actually supports that specific action. A signal that pattern-matches to a known failure may have a different cause.

문단역할
1. 자율 선언"사용자는 실시간으로 보고 있지 않으며 중간 질문에 답할 수 없다" — 이 첫 문장이 효과의 대부분을 담당합니다. 원문 그대로 유지하십시오. 되돌릴 수 있는 작업은 묻지 말고 진행, 파괴적 작업과 진짜 범위 변경에서만 정지.

블록 2 — 산출물의 범위 정의

# Delivering work
The user's request — or the plan they approved — sets the scope, and the scope is the deliverable: don't quietly narrow, widen, or swap it. Read ambiguity the way a careful colleague would: make routine judgment calls yourself, and check in only when different readings would lead to materially different work. If you see a real problem with the task as specified, say so in a sentence or two and keep building under stated assumptions; if the user hears the concern and reaffirms, that is their decision, so deliver the full request.

If a question comes up partway, first do everything that doesn't depend on the answer; then state the assumption you made, or — when going ahead on a wrong guess would be unsafe or would make the work useless — put the question at the end of a turn that also delivers that progress. If one part turns out to be blocked, complete every other part in full and say exactly what you left out and why — the whole task is the deliverable, and scaling it down is the user's call, not yours. A step you have decided on is something to run, not to announce: describing the next step and ending the turn leaves it undone until the user replies.

Keep changes to what the request needs. Something else you notice worth doing — cleanup or documentation the task didn't call for, a change to a file the task didn't require — is a suggestion to make at the end, not a change to make; actions clearly beyond what the ask implies, and risky or destructive ones, still need the user's go-ahead.

핵심 세 문장:

  • 범위가 곧 산출물이다. 조용히 좁히거나 넓히거나 바꿔치기하지 말 것. 모호함은 신중한 동료처럼 읽고, 해석 차이가 실질적으로 다른 결과물을 낳을 때만 확인.
  • 중간에 의문이 생기면 답에 의존하지 않는 것부터 전부 처리한 뒤 가정을 밝히거나, 잘못 추측하면 위험·무의미해지는 경우에만 진척을 함께 전달하는 턴의 끝에 질문을 붙일 것.
  • 일부가 막히면 나머지를 전부 완결하고 무엇을 왜 뺐는지 정확히 말할 것. 작업을 축소하는 판단은 사용자 몫이지 모델 몫이 아니다.

09압축(compaction) 요약에 남길 것 지정

증상 — 클라이언트 압축 요약이 제약·결정·정확한 수치를 누락한다

Fable 5.1은 "요약에 무엇을 반드시 남겨야 하는지"를 명시적으로 알려주면 잘 반응합니다. 서버측 compaction은 이미 이 처리를 합니다. 클라이언트에서 직접 압축한다면 아래 지시문을 쓰십시오.

Summarize the transcript inside <summary></summary> tags. Include relevant information in the summary such that this conversation will be continued by a new context window without needing to redo work or be reprovided with relevant constraints or context. Be sure to preserve: (1) any difficulties or problems that came up, and how they were handled or resolved; (2) any possibilities, options, or approaches that were raised, tried, or set aside, and why; (3) anything that was asked for, decided, agreed, ruled out, or established as a preference, constraint, or boundary — stated exactly; (4) exactly where things stand now — what has been covered, settled, or completed so far; (5) anything still open, unresolved, promised, or expected to happen next; (6) specific details that would be hard to reconstruct — names, numbers, dates, exact wording, links or references — kept exactly. Be complete on these even at the cost of length; keep everything else concise. Weight the two voices differently: keep what the user said, asked for, shared, or established carefully and close to their own words; your own explanations and reasoning can be condensed much further, to what they concluded or produced — as long as nothing in the six items above is dropped.

10변경 범위와 테스트를 요청 범위로 제한

증상 — 요청하지 않은 수정·확장 / 과도한 테스트 파일 커밋

개방형 기능 구현을 시키면 Fable 5.1은 요청받은 것 + 알파를 내놓는 경향이 있습니다. 근처 코드를 고치거나, 언급되지 않은 동작을 확장하거나, 변경 규모에 비해 많은 테스트 파일을 커밋합니다.

공식 문서에 따르면, 아래 지시를 넣으면 요청하지 않은 추가와 커밋되는 테스트 코드가 상당히 줄어들며, 작업 성공률에는 측정 가능한 변화가 없습니다. 이 "성공률 손실 없음"이 이 절의 핵심 근거입니다.

If, while working or testing, you find a pre-existing bug, a performance concern, or behavior the task doesn't mention, don't fix, optimize or extend it in this change unless the requested behavior cannot work without it; report it as a follow-up in your summary. Where the task is ambiguous, implement the reading its wording and the surrounding code most directly support, state that assumption in your summary, and don't build for the other readings as well. Verify your work however you like; scratch scripts and quick checks need not be kept. Commit tests only where the task asks for them or this repository already keeps tests for this kind of change, sized like the neighboring test files — roughly one focused test per stated behavior — and don't turn scratch checks into additional permanent test files. This is about extras only: implement every behavior the task asks for, completely.

규칙 5개:

  1. 기존 버그·성능 이슈·언급 안 된 동작을 발견해도 이번 변경에서는 손대지 않는다. 요청된 동작이 그것 없이는 작동 불가능한 경우만 예외. 나머지는 요약에 후속 과제로 보고.
  2. 모호하면 문구와 주변 코드가 가장 직접적으로 지지하는 해석 하나만 구현하고 요약에 그 가정을 명시. 다른 해석까지 대비해 만들지 말 것.
  3. 검증은 자유롭게. 임시 스크립트와 빠른 확인은 보존할 필요 없음.
  4. 테스트는 과제가 요구했거나 이 저장소가 이미 이런 변경에 테스트를 두는 경우에만 커밋. 크기는 이웃 테스트 파일 수준, 대략 명시된 동작 1개당 집중 테스트 1개. 임시 확인을 영구 테스트 파일로 승격시키지 말 것.
  5. 마지막 문장이 안전장치: "이건 어디까지나 '추가분'에 대한 이야기다. 과제가 요구한 모든 동작은 빠짐없이 완전하게 구현하라." 이 문장이 없으면 모델이 축소 지시로 오독할 수 있습니다.

11low effort에서의 검색 트리거

증상 — low에서 검색하지 않고 기억으로 답한다

low effort에서 Fable 5.1은 Fable 5보다 검색·검색증강(retrieval) 툴을 덜 호출하고 기억에 의존해 답할 가능성이 높습니다.

대응 1 — 해당 턴만 effort 상향

가장 단순한 해법은 대화 전체가 아니라 문제가 되는 턴만 effort를 올리는 것입니다. Fable 5.1은 메시지 단위 effort 변경(베타 헤더 mid-conversation-output-config-2026-07-01)을 지원하며, 이 방식은 프롬프트 캐시를 유지합니다.

messages=[
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."},
    # 빈 content + output_config만 담은 시스템 메시지.
    # 다음 user 턴부터 새 레벨이 적용된다.
    {"role": "system", "content": [], "output_config": {"effort": "high"}},
    {"role": "user", "content": "..."},
]
주의

최상위 output_config.effort 값을 요청 사이에 바꾸는 방식은 캐시를 재시작시키고, 스티어링도 덜 안정적입니다. 모델의 앞선 답변들이 이전 레벨에서 쓰인 것이라, 모델이 그것들과 일관성을 유지하려는 경향이 있기 때문입니다. Fable 5.1에서는 메시지 단위 변경을 우선하십시오.

대응 2 — 검증을 유도하는 프롬프트

When a query centers on a name you do not confidently recognize, or recognize from a fast-moving area like AI models and developer tools where the landscape shifts within months, the name itself is the thing to verify: search before answering, and include the name as the user wrote it in at least one query alongside any reformulations. This holds even when you have some background on it — partial background is exactly what makes an out-of-date answer sound authoritative, so familiarity is not a reason to skip the search.

해설: 질의의 중심에 확신 없이 아는 이름이 있거나, AI 모델·개발자 도구처럼 몇 달 단위로 지형이 바뀌는 영역의 이름이 있다면 — 그 이름 자체가 검증 대상이다. 답하기 전에 검색하고, 재구성한 질의들과 함께 사용자가 쓴 표기 그대로를 최소 한 개의 쿼리에 포함하라. 배경 지식이 조금 있어도 마찬가지다. 부분적 배경 지식이야말로 낡은 답변을 권위 있게 들리게 만드는 원인이므로, 익숙함은 검색을 건너뛸 이유가 되지 않는다.

12세이프가드 오탐 줄이기

증상 — 정상 코딩 요청이 stop_reason: "refusal"로 막힌다

Fable 5.1의 안전 분류기는 출시 당시의 Fable 5보다 오탐(false positive)이 적고, 소스 코드에서 취약점을 찾는 작업은 허용됩니다. 그럼에도 오탐은 발생하며, 차단된 요청은 stop_reason: "refusal"을 반환합니다.

오탐 유발 상황대처
컴파일 확인 표현 "Does this program compile without errors?"(이 프로그램이 오류 없이 컴파일되나?) 대신 "Are there any bugs in this program?"(이 프로그램에 버그가 있나?)로 질문하십시오.
덜 알려진 프로그래밍 언어 그 언어가 무엇이고 어떻게 동작하는지 컨텍스트를 제공하십시오. 예: 해당 언어의 공식 문서에 접근 권한을 줌.
툴 출력의 Base64 base64로 인코딩된 데이터를 모델 컨텍스트에 반환하는 툴이 오탐을 유발합니다. 제거하는 것이 권장 해법입니다.

Anthropic은 Fable 5.1을 안전장치와 함께 출시했으며, 일부 주제의 질의는 차선 모델인 Claude Opus 5의 응답으로 전환(routing)됩니다. 이 안전장치는 보수적으로 튜닝되어 있어 무해한 요청도 가끔 걸리지만, 평균적으로 세션의 5% 미만에서 발동합니다. 사용자가 Fable을 선택했는데 다른 모델 응답이 오는 상황은 여기서 비롯됩니다.

13전체 재작성 대신 부분 편집

증상 — 작은 수정인데 파일 전체를 다시 쓴다

Fable 5.1은 Fable 5보다 텍스트 파일 전체를 다시 쓸 가능성이 높습니다. 결과 파일은 대개 동일합니다. 하지만 파일이 짧거나 대부분이 바뀌는 경우가 아니라면, 전체 재작성은 출력 토큰과 시간을 더 씁니다. 아래 지시는 소·중 규모 변경에서 5.1의 동작을 5 수준으로 되돌립니다.

시스템 프롬프트 또는 첫 user 메시지 끝에 추가

The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing.

해설: "다른 조건이 같다면 파일 편집에 쓰는 토큰 수는 최소화하는 것이 좋다. 따라서 최종 결과에 영향이 없는 한 전체를 다시 쓰지 말고 외과적으로 편집하라." 조건절("최종 결과에 영향이 없는 한")이 있어야 품질을 희생하지 않습니다.

14xhigh/max에서 긴 출력의 여유 공간

증상 — 긴 산출물이 오래 걸리거나 max_tokens에 걸린다

xhigh, 특히 max에서 Fable 5.1은 답변을 쓰기 시작하기 전에 더 오래 사고할 수 있습니다. 하나의 요청이 긴 산출물(예: 긴 문서 전체 재작성)을 요구하면, 모델이 그 산출물의 상당 부분을 사고 과정에서 초안으로 작성한 뒤 답변에서 다시 씁니다. 대기 시간이 길어지고 출력 토큰이 두 배로 듭니다.

1순위 해법

이런 요청은 권장 시작점인 high에서 돌리십시오. xhigh나 max로 올리는 것은 품질 향상을 실제로 측정한 경우에만. 대부분의 "긴 문서 생성"은 high가 최적입니다.

그래도 xhigh/max로 돌려야 한다면

  1. max_tokens를 예상 답변 길이가 아니라 "사고 + 답변"을 합친 크기로 잡을 것. max_tokens는 총 출력의 하드 리밋입니다.
  2. 아래 노트를 user 메시지 끝에 붙일 것. [max_tokens]를 실제 값(예: 64,000)으로 치환해야 합니다.
Everything produced in one reply, including any reasoning or drafting done before the reply, counts toward a single limit of about [max_tokens] tokens. If that limit is reached before the reply is finished, the person receives a cut-off response and has to start over. Composing an entire output or deliverable in full as reasoning and then again as a reply would double the length of the turn without improving the result, so don't do that.

Instead, when the person has asked for a long or effort-intensive deliverable such as a multi-section document, a large table or dataset, or a complete code file, spend extra effort on understanding the request, checking the inputs the answer depends on, settling the structure and other difficult decisions, and otherwise using the reasoning space to reason and the output space to write an output. Usually it is not needed to draft an output multiple times.

해설: ① 답변 전 추론·초안까지 전부 하나의 약 [max_tokens] 한도에 합산된다 ② 한도에 먼저 도달하면 사용자는 잘린 응답을 받고 처음부터 다시 해야 한다 ③ 산출물을 추론에서 한 번, 답변에서 또 한 번 완전히 작성하면 결과 개선 없이 턴 길이만 두 배가 되니 그러지 말 것 ④ 대신 요청 이해, 의존 입력 확인, 구조와 어려운 결정 확정에 추론 공간을 쓰고 출력 공간은 출력을 쓰는 데 쓸 것.

15서브에이전트 대기 없이 병행

증상 — 서브에이전트가 도는 동안 리드 에이전트가 유휴 상태

코딩 에이전트가 Fable 5.1에게 서브에이전트 위임을 허용한다면, 리드 에이전트가 각 서브에이전트를 기다리며 멈추게 만들지 마십시오. 코딩 작업에서 리드가 계속 일하도록 두면 비슷한 품질·토큰 사용량·비용으로 평균 완료 시간이 낮아집니다.

구성 3단계

  1. 서브에이전트를 시작하는 툴이 즉시 반환하도록 만든다.
  2. 각 서브에이전트의 결과가 준비되면 이후의 user 메시지로 리드에게 전달한다.
  3. 리드가 결과를 기다리고 싶을 때 호출할 수 있는 별도의 대기 툴을 준다.
기대치 조정

이렇게 구성해도 모델은 여전히 자주 기다리는 쪽을 택합니다. 시간 절감은 "모델이 다른 일을 이어서 하기로 결정한 실행분"에서 나옵니다. 즉 이 최적화는 모든 실행이 아니라 일부 실행에서만 이득이 나며, 그 평균이 개선되는 구조입니다. 도입 후 "왜 여전히 기다리지?"라고 오판하지 않도록 이 점을 알아두십시오.

비판

이 문서에 실린 프롬프트 블록들은 서로 충돌하며, 전부 넣으면 성능이 떨어질 가능성이 크다.

문서 구조가 "증상 → 처방" 인덱스인 것은 우연이 아닙니다. 모두 적용하라는 뜻이 아니라는 신호입니다. 그런데 실무에서는 "공식 권장 프롬프트"라는 이유로 전부 복사해 시스템 프롬프트에 쌓는 일이 빈번합니다. 그 결과는 다음과 같습니다.

  1. 직접 충돌. 8절 블록 1은 질문하지 말고 진행하라고 지시합니다. 8절 블록 2는 해석 차이가 실질적 차이를 낳으면 확인하라고 지시합니다. 10절은 모호하면 해석 하나만 골라 진행하라고 합니다. 셋 다 넣으면 모델은 "묻지 마 / 물어봐 / 고르고 가"를 동시에 받습니다. 공식 문서 자신도 8절 블록 1에 대해 "모호한 요청에 질문을 덜 하게 만들 수 있으니 트레이드오프를 확인하라"고 경고합니다. 이 경고는 다른 블록과 합쳤을 때 더 커집니다.
  2. 토큰 예산 잠식. 8·9·10·14절 블록만 합쳐도 상당한 분량입니다. 이것이 모든 요청에 상시 적재되면서 캐시 접두부를 키우고, 정작 작업 지시의 비중을 희석시킵니다. 14절은 토큰 낭비를 줄이려는 절인데, 그 처방 자체가 토큰을 소비하는 아이러니가 있습니다.
  3. 측정 없는 이식. 문서 전체가 "당신의 평가셋으로 검증하라"를 반복합니다. 그런데 현장 대부분에는 평가셋이 없습니다. 평가셋 없이 프롬프트를 쌓는 것은 개선이 아니라 무작위 변경이며, 어느 블록이 이득이고 어느 블록이 손해인지 영원히 알 수 없게 됩니다.
