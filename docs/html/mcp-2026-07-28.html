0130초 요약

  1. 세션이 없어졌다. initialize/initialized 핸드셰이크와 Mcp-Session-Id 헤더가 제거됐다. 모든 요청이 자기 자신을 설명하므로 평범한 라운드로빈 로드밸런서 뒤 아무 인스턴스나 처리할 수 있다.
  2. 서버가 사용자에게 되묻는 방식이 바뀌었다. SSE 스트림을 열어두는 대신, 서버가 "입력 필요" 응답을 돌려주고 클라이언트가 답을 붙여 원래 호출을 재시도한다(MRTR).
  3. 게이트웨이가 본문을 뜯지 않아도 된다. 메서드와 툴 이름이 Mcp-Method·Mcp-Name HTTP 헤더로 이동했다.
  4. 목록 응답에 캐시 힌트가 붙었다. ttlMs·cacheScope로 툴 카탈로그를 캐싱할 수 있다.
  5. 파괴적 변경이지만 마지막이 목표다. 확장(Extensions) 프레임워크와 최소 12개월 폐기 유예의 수명주기 정책이 함께 도입됐다.

규모 지표: Tier 1 SDK 합계 월 다운로드가 5억 건에 근접하고, TypeScript·Python SDK는 누적 10억 건을 넘었다.

02요청 형태의 변화

이전 버전에서는 툴을 한 번 호출하려면 먼저 세션을 세워야 했다. initialize로 세션을 열고, 서버가 발급한 Mcp-Session-Id를 이후 모든 요청에 실어야 하며, 그 헤더가 클라이언트를 발급한 인스턴스에 고정시켰다.

2026-07-28 방식 — 자기 완결적 단일 요청

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search","arguments":{"q":"otters"},
 "_meta":{"io.modelcontextprotocol/clientInfo":{"name":"my-app","version":"1.0"}}}}

프로토콜 버전, 클라이언트 신원, 클라이언트 기능이 전부 _meta에 실려 매 요청마다 함께 이동한다. 스티키 라우팅과 공유 세션 저장소는 프로토콜 계층에서 더 이상 필요하지 않다.

03무상태 코어BREAKING

핸드셰이크 제거 SEP-2575
initialize/notifications/initialized 교환이 사라졌다. 대신 io.modelcontextprotocol/protocolVersion, io.modelcontextprotocol/clientCapabilities 같은 _meta 키로 매 요청이 스스로를 설명한다.
세션 제거 SEP-2567
Streamable HTTP에서 Mcp-Session-Id 헤더와 프로토콜 수준 세션이 제거됐다. tools/list·resources/list·prompts/list는 이제 연결마다 다른 결과를 주지 않는다.
선택적 사전 조회 NEW
클라이언트가 먼저 서버 기능을 알아야 하면 새 RPC server/discover를 호출한다. 필수가 아니다.

무상태 프로토콜, 상태를 가진 애플리케이션

프로토콜에서 세션이 빠졌다는 것이 애플리케이션이 무상태여야 한다는 뜻은 아니다. 호출 간에 상태를 이어가야 하면 HTTP API가 늘 해온 방식을 쓴다 — 툴이 명시적 핸들(basket_id, browser_id 같은 식별자)을 발급하고, 모델이 그 값을 다음 호출의 일반 인자로 되돌려 넘긴다.

메인테이너들은 이 방식이 단순한 대체재가 아니라 더 나은 설계라고 본다. 트랜스포트 메타데이터에 숨겨진 세션 상태와 달리 모델이 핸들을 볼 수 있어서, 여러 툴에 걸쳐 핸들을 조합하고 단계 사이로 넘길 수 있다.

달라지는 책임: 상태 관리가 프로토콜에서 애플리케이션으로 내려왔다. 핸들의 발급·검증·만료·권한 확인을 서버가 직접 설계해야 한다. 프로토콜이 대신 해주지 않는다.

04MRTR — Multi Round-Trip RequestsBREAKING

툴 실행 중간에 사용자 확인이나 누락된 파라미터가 필요할 때가 있다. 이전에는 서버가 elicitation/create, sampling/createMessage, roots/list를 클라이언트로 밀어내려면 스트림을 열어두어야 했다. MRTR은 그 흐름을 무상태로 재구성한다. SEP-2322

  1. 서버가 resultType: "input_required"와 필요한 요청 목록, 그리고 재개용 requestState를 반환한다.
  2. 클라이언트가 사용자에게 물어 답을 모은다.
  3. 클라이언트가 inputResponses와 에코된 requestState를 붙여 원래 호출을 재시도한다.
{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "type": "elicitation",
      "message": "Delete 3 files?",
      "schema": { "type": "boolean" }
    }
  },
  "requestState": "eyJzdGVwIjoxLCJmaWxlcyI6WyJhIiwiYiIsImMiXX0="
}

재시도에 필요한 모든 것이 페이로드 안에 있으므로 어느 서버 인스턴스가 받아도 이어서 처리할 수 있다. 스키마상 타입은 InputRequiredResult다.

함께 조여진 규칙 하나 SEP-2260: 서버 발신 요청은 서버가 클라이언트 요청을 실제로 처리하고 있는 동안에만 낼 수 있다. 이전 버전에서는 권고였고 이제는 필수다. 사용자가 맥락 없이 갑자기 확인 창을 받는 일이 없고, 모든 확인 요청은 사용자나 그 에이전트가 시작한 동작으로 추적된다.

05헤더 기반 라우팅BREAKING

Streamable HTTP 요청은 Mcp-Method와 Mcp-Name 헤더를 반드시 포함해야 한다. SEP-2243

  • 게이트웨이·레이트리미터·WAF가 JSON 본문을 파싱하지 않고 헤더만으로 라우팅하고 계량할 수 있다.
  • 헤더와 본문의 내용이 어긋나면 서버가 요청을 거부한다.

운영 관점에서 이 변경의 의미가 크다. 툴 단위 레이트리밋, 툴 단위 인가, 툴별 백엔드 분리가 애플리케이션 코드가 아니라 인프라 계층의 설정 문제로 내려온다.

06목록 결과 캐싱

tools/list, prompts/list, resources/list, resources/read 응답에 ttlMs와 cacheScope가 붙는다. HTTP Cache-Control을 본뜬 설계다. SEP-2549

  • ttlMs — 응답이 신선한 기간
  • cacheScope — 사용자 간 공유가 안전한지 여부
  • 결정적(deterministic) 순서가 보장되므로, 재접속 후에도 상위 프롬프트 캐시가 흔들리지 않는다

부수 효과로, 목록이 바뀐 것을 알아내기 위해 장기 SSE 스트림을 유지하는 것이 유일한 방법이 아니게 됐다.

07인가 강화

메인테이너들은 지난 1년간 구현자들과 논의한 결과, 통합 시간의 대부분이 인가에서 소모된다고 판단했다. 이번 개정은 OAuth 2.0과 OpenID Connect의 실제 배포 관행에 더 가깝게 맞추는 데 집중했다.

08확장 프레임워크가 정식화됐다

확장은 이전 버전에도 있었지만 절차가 없었다. 이번에 형식이 확정됐다. SEP-2133

  • 역방향 DNS 형태의 ID로 식별한다 (예: io.modelcontextprotocol/tasks)
  • 클라이언트·서버 capabilities의 extensions 맵으로 협상한다
  • 별도 ext-* 저장소에서 위임된 메인테이너가 관리하고, 사양과 독립적으로 버전을 올린다
  • SEP 프로세스에 Extensions Track이 신설돼, 실험 단계에서 공식 단계로 가는 경로가 생겼다

09Tasks — 실험적 코어에서 확장으로BREAKING

Tasks는 이전 버전에서 실험적 코어 기능으로 출시됐다. 실제 프로덕션 사용에서 재설계가 필요하다는 것이 드러나, 사양 본문이 아니라 확장(io.modelcontextprotocol/tasks)이 적절한 자리라고 판단했다.

  • 서버가 tools/call에 태스크 핸들로 응답할 수 있고, 클라이언트가 tasks/get(폴링), tasks/update, tasks/cancel로 진행한다
  • 태스크 생성은 서버 주도다. 클라이언트가 확장 지원을 알리면, 어떤 호출을 태스크로 돌릴지는 서버가 결정한다
  • tasks/list는 제거됐다 — 세션이 없으면 스코프를 안전하게 한정할 수 없기 때문이다
  • 변경 알림이 기존 HTTP GET 엔드포인트에서 단일 subscriptions/listen 스트림으로 이동했고, 클라이언트가 알림 유형별로 옵트인한다
마이그레이션 필요 이전 버전의 실험적 Tasks API로 구현한 코드는 새 수명주기로 옮겨야 한다. 실험적 기능이었으므로 12개월 폐기 유예의 보호를 받지 않는다.

10폐기와 수명주기 정책

폐기된 기능 SEP-2577

기능권고 대체 수단
Roots툴 파라미터, 리소스 URI, 또는 서버 설정
SamplingLLM 제공자 API를 직접 통합
Loggingstdio 트랜스포트는 stderr, 구조적 관측은 OpenTelemetry
HTTP+SSE 트랜스포트Streamable HTTP (레거시 트랜스포트는 1년 오프램프)

이들은 표기상의 폐기다. 메서드·타입·capability 플래그는 이번 릴리스에서 그대로 동작하고, 최소 12개월간 유지된다. 실제 제거에는 수명주기 정책에 따른 별도 SEP이 필요하다. 다만 새로 만드는 구현에서는 채택하지 않는 것이 권고다.

수명주기 정책 SEP-2596

모든 기능이 Active → Deprecated → Removed 수명주기를 갖고, 폐기 시점부터 가장 이른 제거 시점까지 최소 12개월이 보장된다. 사후 대응이 아니라 계획을 세울 수 있게 하는 장치다.

여기에 두 가지가 더해진다. 새 기능은 옵트인 확장으로 먼저 출시해 거기서 안정화할 수 있고(경우에 따라 사양 본문으로 들어오지 않을 수도 있다), Standards Track SEP는 적합성 테스트 스위트(conformance suite)에 해당 시나리오가 들어오기 전에는 Final 상태에 이를 수 없다. SEP-2484 이 스위트는 공식 SDK 등급제가 SDK를 채점하는 기준과 같은 것이다.

메인테이너의 입장 요약: 이번처럼 파괴적인 변경은 예외로 두겠다는 것이다. 2026-07-28을 타깃으로 구현하면 이후 개정에서 트랜스포트나 수명주기 코드를 다시 쓰지 않아도 되게 하는 것이 목표로 제시됐다.

11그 외 변경

툴 스키마가 JSON Schema 2020-12 전체로 확장 SEP-2106
툴의 inputSchema·outputSchema가 완전한 JSON Schema 2020-12가 됐다. 입력 스키마는 루트가 type: "object"여야 하는 제약을 유지하지만 oneOf·anyOf·allOf 조합, 조건부, $ref·$defs 참조를 쓸 수 있다. 출력 스키마는 제약이 없고, structuredContent가 객체가 아닌 임의의 JSON 값이어도 된다. 구현체는 외부 $ref URI를 자동 역참조해서는 안 되며, 스키마 깊이와 검증 시간에 상한을 두는 것이 권고다.
오류 코드 변경 SEP-2164BREAKING
리소스를 찾지 못했을 때의 코드가 MCP 고유값 -32002에서 JSON-RPC 표준 -32602(Invalid Params)로 바뀌었다. 클라이언트가 -32002 리터럴로 분기한다면 수정해야 한다.
W3C Trace Context 전파 문서화 SEP-414
_meta에 담기는 traceparent·tracestate·baggage 키 이름이 사양에 고정됐다. 이미 일부 SDK와 도구가 하던 일이지만, 키 이름이 확정되면서 호스트 애플리케이션에서 시작된 트레이스가 클라이언트 SDK → MCP 서버 → 서버가 호출하는 하위 시스템까지 이어져 OpenTelemetry 호환 백엔드에서 하나의 span 트리로 보인다.

16폐쇄망·게이트웨이 관점 검토

이 절은 원문에 없는 내용으로, 사내 폐쇄망 환경과 API 게이트웨이 구축 맥락에 대입한 검토다.

유리해지는 것

  • 게이트웨이 필터가 단순해진다. Mcp-Method·Mcp-Name이 헤더에 오므로, 툴 단위 레이트리밋·서킷브레이커·라우팅을 본문 파싱 없이 헤더 조건으로 구성할 수 있다. JSON 본문을 읽는 커스텀 필터를 만들 필요가 사라진다.
  • 세션 저장소가 필요 없다. 스티키 세션과 공유 세션 스토어(Redis 등)를 프로토콜 때문에 두던 이유가 없어진다. 인스턴스를 늘리는 것이 곧 처리량 증가가 된다.
  • Sampling 폐기의 영향이 작다. 폐쇄망에서 이미 로컬 추론 서버를 직접 호출하는 구조라면, 권고 대체 수단(LLM 제공자 API 직접 통합)과 이미 일치한다.
  • 목록 캐싱이 대역폭을 줄인다. ttlMs·cacheScope로 툴 카탈로그 재조회를 줄일 수 있다.

확인이 필요한 것

  • CIMD 이행이 폐쇄망에서 문제가 될 수 있다. DCR이 폐기되고 Client ID Metadata Documents가 표준이 된다. CIMD는 클라이언트 메타데이터 문서를 조회 가능한 위치에 게시하는 방식이므로, 외부로 나갈 수 없는 환경에서는 내부에서 호스팅하고 내부 인가 서버가 그것을 해석하도록 설계해야 한다. DCR이 하위 호환으로 남아 있는 동안 이행 경로를 먼저 확정해 두는 것이 안전하다.
  • Logging 폐기는 관측 스택 준비를 요구한다. 구조적 관측의 권고 대체가 OpenTelemetry이므로, 폐쇄망 내부에 OTel 컬렉터와 백엔드가 필요하다. Trace Context 키 이름이 사양에 고정된 것은 이 방향과 맞물린다.
  • 상태 관리 책임이 애플리케이션으로 내려온다. 명시적 핸들 패턴을 쓰면 핸들의 발급·검증·만료·소유자 확인을 직접 구현해야 한다. 모델이 핸들 값을 보게 되므로, 핸들 자체가 권한을 담지 않도록(추측·재사용 불가하도록) 설계해야 한다.
  • 게이트웨이가 헤더/본문 불일치를 어떻게 다룰지 정해야 한다. 사양은 서버가 불일치 요청을 거부하도록 한다. 게이트웨이에서 헤더를 다시 쓰는 필터를 넣으면 그 자체가 사양 위반 요청을 만들 수 있다.
아래 예시는 개념 설명용이다 헤더 조건 라우팅의 형태를 보이기 위한 것으로, 프로퍼티 경로와 predicate 표기는 사용 중인 Spring Cloud 버전의 공식 문서로 확인해야 한다. YAML 문법만 검증했고, 해당 버전에서의 동작은 검증하지 못했다. 
spring:
  cloud:
    gateway:
      mvc:
        routes:
          - id: mcp-tools-call
            uri: http://mcp-tool-pool
            predicates:
              - Path=/mcp
              - Method=POST
              - Header=Mcp-Method, tools/call
          - id: mcp-discover
            uri: http://mcp-meta-pool
            predicates:
              - Path=/mcp
              - Method=POST
              - Header=Mcp-Method, server/discover
