00promptfoo란 무엇인가개념

LLM 애플리케이션을 테스트하는 오픈소스 CLI다. 프롬프트·모델·테스트 케이스·채점 기준을 YAML 한 파일에 적어 두면, 명령 한 줄로 모든 케이스를 실행하고 결과를 표로 보여 준다. 채팅 UI에서 프롬프트를 이리저리 바꿔 보며 눈으로 확인하던 작업을 재실행 가능한 테스트로 바꾸는 도구다.

무엇을 해결하나

지금 겪는 문제promptfoo가 하는 일
프롬프트를 한 줄 고쳤더니 다른 케이스가 깨졌는데 모른다고칠 때마다 전 케이스를 자동 재채점한다(회귀 테스트)
어떤 모델이 우리 작업에 맞는지 감으로 고른다같은 케이스를 여러 모델에 동시에 돌려 정확도·비용·지연을 한 표에 놓는다
"규정 밖 약속 금지" 같은 태도 기준은 코드로 못 잡는다코드형 검사(문자열·JSON·정규식)와 AI 채점(llm-rubric)을 같은 파일에서 섞어 쓴다
탈옥·개인정보 유출을 배포 전에 점검할 방법이 없다redteam으로 수십 종 공격을 자동 생성해 취약점 보고서를 만든다
배포 전에 사람이 직접 몇 개 찔러 보고 끝낸다CI에서 실행해 실패하면 빌드를 막는다(종료 코드 100)

한 문장 요약

질문(테스트 케이스)과 채점표(단언)를 같은 파일에 적고, promptfoo eval로 채점하고, promptfoo view로 결과를 본다. 발표 자료 5부에서 말한 "프롬프트와 평가는 앞뒷면"이 물리적으로 파일 하나가 되는 지점이다.

01설치와 API 키 준비10분

설치 방법 세 가지

Node.js 22.22 이상이 필요하다(24 LTS 권장). 버전 확인은 node -v.

# 방법 1 - 설치 없이 바로 실행 (가장 빠름, 매번 최신 버전)
npx promptfoo@latest --version

# 방법 2 - 전역 설치 (promptfoo 명령을 그대로 쓴다)
npm install -g promptfoo
promptfoo --version

# 방법 3 - macOS Homebrew
brew install promptfoo

이 문서의 예시는 전역 설치 기준으로 promptfoo ...라고 쓴다. npx를 쓰면 앞에 npx promptfoo@latest를 붙이면 된다.

API 키 등록

모델을 호출하려면 해당 제공자의 API 키가 환경 변수로 있어야 한다. 키는 설정 파일에 적지 말고 셸에 등록한다.

제공자환경 변수비고
Anthropic (Claude)ANTHROPIC_API_KEY이 문서 예시의 기본 모델
OpenAIOPENAI_API_KEYAI 채점·레드팀 공격 생성의 기본 채점자로도 쓰인다
GoogleGOOGLE_API_KEYGemini 계열
로컬 Ollama없음ollama:chat:모델명 형식, 키 불필요
 
# macOS / Linux (zsh) - ~/.zshrc 에 추가 후 새 터미널
export ANTHROPIC_API_KEY="sk-ant-..."
export OPENAI_API_KEY="sk-..."

# Windows PowerShell - 영구 등록 후 새 터미널
setx ANTHROPIC_API_KEY "sk-ant-..."
setx OPENAI_API_KEY "sk-..."
채점자 키에 대해

AI 채점(llm-rubric 등)은 기본적으로 OpenAI 모델을 채점자로 쓴다. OpenAI 키가 없고 Anthropic 키만 있으면 promptfoo가 자동으로 Anthropic을 채점자로 고른다. 명시적으로 지정하려면 3절의 defaultTest.options.provider를 쓴다.

025분 시작 - init, eval, view따라하기

  1. 예제 프로젝트 생성 - 폴더 하나에 설정 파일과 프롬프트가 만들어진다. 
    promptfoo init --example getting-started
cd getting-started
  2. 평가 실행 - 설정 파일의 모든 프롬프트 × 모델 × 테스트 조합을 호출하고 채점한다. 터미널에 합격/실패 요약이 찍힌다. 
    promptfoo eval
  3. 결과 보기 - 브라우저 뷰어가 열린다. 행은 테스트 케이스, 열은 프롬프트·모델 조합, 셀은 출력과 채점 결과. 
    promptfoo view

결과 화면 읽는 법

  • 셀 색 - 통과는 초록, 실패는 빨강. 셀을 클릭하면 원본 출력, 각 단언의 통과 여부와 사유, 지연 시간, 토큰과 비용이 보인다.
  • 상단 합계 - 조합별 합격률. 두 프롬프트 버전을 나란히 놓으면 어느 쪽이 몇 케이스를 더 통과했는지 바로 비교된다.
  • 파일로 남기기 - promptfoo eval -o result.json 또는 -o result.html. CI 산출물로 보관할 때 쓴다.

빈 프로젝트에서 시작하기

mkdir my-eval && cd my-eval
promptfoo init          # 대화형으로 설정 파일 생성
promptfoo eval setup    # 대신 웹 UI로 설정을 만들고 싶을 때

03설정 파일 해부 - promptfooconfig.yaml핵심

파일 하나가 네 블록으로 이뤄진다. prompts(무엇을 물을지), providers(누구에게), tests(어떤 입력으로, 무엇을 검사할지), defaultTest(전 테스트 공통 설정). 발표 자료 82페이지의 고객 상담 예시를 그대로 옮기면 이렇다.

# promptfooconfig.yaml
description: 고객 상담 봇 - 환불 규정 준수 검사

prompts:
  - "당신은 CS 상담원입니다. 규정 외 약속은 금지합니다. 문의: {{query}}"

providers:
  - anthropic:messages:claude-sonnet-4-6

tests:
  - vars:
      query: "어제 산 제품 환불 되나요?"
    assert:
      - type: contains          # 코드형 - 규정 수치가 들어 있어야 한다
        value: "14일"
      - type: llm-rubric        # AI 채점 - 태도 기준
        value: "환불 규정을 정확히 안내하고, 규정에 없는 약속을 하지 않는다"
      - type: latency           # 성능 게이트 - 3초 이내
        threshold: 3000

블록별 설명

블록역할자주 쓰는 형태
prompts모델에 보낼 프롬프트. {{변수}} 자리에 tests의 vars가 들어간다. 여러 개 적으면 버전 비교가 된다.인라인 문자열, file://prompts/v1.txt, 채팅 형식 JSON 파일
providers호출할 모델. 여러 개면 모델 비교 매트릭스가 된다.anthropic:messages:claude-sonnet-4-6, openai:chat:gpt-5.4, ollama:chat:llama3.3, file://my_provider.py, HTTP 엔드포인트
tests입력 변수와 단언 목록. 단언이 없어도 실행되며 뷰어에서 사람이 직접 판정할 수 있다.인라인, file://tests.csv, file://tests/*.yaml
defaultTest모든 테스트에 공통 적용되는 단언·변수·옵션. 채점자 모델과 합격선을 여기서 정한다.options.provider, threshold, 공통 assert

채점자 모델과 합격선 지정

defaultTest:
  threshold: 0.8                       # 가중 평균 80% 이상이면 케이스 통과
  options:
    provider: anthropic:messages:claude-sonnet-4-6   # llm-rubric 등 AI 채점에 쓸 모델
  assert:
    - type: not-contains               # 전 케이스 공통 금지어
      value: "무조건 환불"
구현 모델과 채점 모델을 분리하라

답을 만든 모델이 자기 답을 채점하면 후하게 준다(자기 채점 편향). providers의 모델과 defaultTest.options.provider의 모델을 다르게 두거나, 최소한 채점 기준을 구체적 문장으로 적어 여지를 줄인다.

테스트를 CSV로 관리하기

케이스가 스무 개를 넘으면 YAML보다 표가 편하다. 열 이름이 변수가 되고, __expected 열이 단언이 된다.

# tests.csv
query,__expected,__expected2,__description
"어제 산 제품 환불 되나요?","contains: 14일","llm-rubric: 규정 외 약속 없음","환불 기본"
"영수증 없이 환불 되나요?","contains: 영수증","not-contains: 무조건","영수증 없음"

# promptfooconfig.yaml
tests: file://tests.csv

그 밖의 특수 열: __threshold(케이스별 합격선), __metadata:category(필터용 태그). JSON·JSONL·xlsx·동적 생성 스크립트(file://gen.js)도 같은 자리에 올 수 있다.

04단언(assert) 카탈로그레퍼런스

단언은 두 부류다. 결정론 검사는 코드가 판정하므로 빠르고 공짜이며 결과가 항상 같다. 모델 채점은 LLM이 판정하므로 태도·품질 같은 기준을 잡을 수 있지만 비용이 들고 흔들린다. 원칙은 "코드로 잡을 수 있는 건 코드로, 나머지만 AI로".

결정론 검사

type판정 내용예
equals출력이 값과 정확히 일치value: "4"
contains / icontains부분 문자열 포함 (icontains는 대소문자 무시)value: "14일"
contains-all / contains-any목록의 전부 / 하나 이상 포함value: ["가격", "배송"]
regex정규식 일치value: "^\\d{3}-\\d{4}$"
starts-with지정 문자열로 시작value: "안녕하세요"
is-json / contains-json유효한 JSON인지, JSON을 포함하는지. value에 JSON Schema를 주면 구조까지 검사value: {required: [id, total]}
javascript / python직접 쓴 함수가 참을 반환하면 통과. output 변수로 응답 접근value: output.length < 300
latency응답 시간이 threshold(ms) 이하threshold: 3000
cost호출 비용이 threshold(USD) 이하threshold: 0.002
levenshtein기준 문장과의 편집 거리가 threshold 이하value: "정답", threshold: 5
rouge-n / bleu요약·번역 유사도 지표value: 기준문, threshold: 0.6
is-refusal모델이 답변을 거부했는지 (안전 테스트에서 "거부해야 통과")value 없음
webhook외부 URL에 출력을 보내 판정 받기value: https://.../check

모델 채점

type판정 내용예
llm-rubric자유 문장 기준으로 채점. 가장 많이 쓴다value: "규정 외 약속이 없다"
factuality기준 답과 사실 관계가 맞는지value: "승인권자는 부서장"
answer-relevance질문에 직접 답하는지threshold: 0.9
context-faithfulnessRAG 출력이 주어진 문맥에 근거하는지 (환각 검출)threshold: 0.7
context-recall / context-relevance검색된 문맥이 답에 필요한 정보를 담는지 / 불필요한 문맥이 적은지threshold: 0.8

조합 문법

assert:
  - type: not-contains              # 어떤 type이든 앞에 not- 을 붙이면 부정
    value: "죄송하지만 모릅니다"
  - type: llm-rubric
    value: "존댓말을 쓴다"
    weight: 2                        # 가중치 - 합격선 계산에서 두 배로 센다
  - type: javascript
    value: output.length > 50
    weight: 0                        # 0이면 참고 지표만 기록, 합격 여부에 영향 없음
    metric: length
  - type: assert-set                 # 묶음 - 안의 75% 이상 통과하면 이 묶음 통과
    threshold: 0.75
    assert:
      - type: contains
        value: "배송"
      - type: is-json
      - type: contains
        value: "가격"
      - type: contains
        value: "재고"

케이스의 최종 점수는 (가중치 × 통과) 합계 ÷ 가중치 합계. threshold(기본 1.0)를 넘으면 통과다.

05활용 A - 프롬프트 회귀 테스트가장 흔한 용도

목표는 하나다. 프롬프트를 고칠 때마다 전 케이스를 자동으로 다시 채점해서, 한 케이스를 살리려다 다른 케이스를 죽이는 일을 잡는다.

구성

  1. 골든셋 만들기 - 실제 사용자 문의 중 대표적인 것 10~20개를 CSV로. 실패했던 사례를 우선 넣는다. 생성은 AI에 시켜도 되지만 기대 답은 사람이 검수한다.
  2. 프롬프트를 파일로 - prompts/cs.txt처럼 파일로 빼고 설정에서 file://로 참조한다. 버전 관리가 된다.
  3. 감시 모드로 편집 - 파일이 바뀔 때마다 자동 재실행. 
    promptfoo eval --watch
  4. 실패한 것만 다시 - 고친 뒤 실패했던 케이스만 재실행해 빠르게 확인. 
    promptfoo list evals                        # 직전 실행의 ID 확인
promptfoo eval --filter-failing eval-abc123   # 그 실행에서 실패한 케이스만 (결과 JSON 경로도 가능)

두 버전을 나란히 비교

prompts:
  - file://prompts/cs-v1.txt
  - file://prompts/cs-v2.txt        # 열이 두 개 생긴다 - 같은 케이스에 대한 v1/v2 출력과 점수

providers:
  - anthropic:messages:claude-sonnet-4-6

tests: file://tests/golden.csv

promptfoo view에서 케이스별로 어느 버전이 통과했는지 한눈에 보인다. 합격률이 오르되 기존 통과 케이스가 깨지지 않았을 때만 v2로 교체한다.

캐시 주의

같은 프롬프트·같은 입력은 디스크 캐시(~/.promptfoo/cache)에서 응답을 재사용한다. 비용은 아끼지만 모델의 비결정성을 보고 싶을 땐 --no-cache, 흔들림 자체를 측정하려면 --repeat 5.

06활용 B - 모델 비교와 비용·속도 게이트선택 근거 만들기

providers에 모델을 여러 개 적으면 같은 테스트가 모델 수만큼 열로 늘어난다. 정확도만이 아니라 cost·latency 단언을 함께 걸어 "우리 예산과 응답 시간 안에서 가장 잘하는 모델"을 고른다.

providers:
  - anthropic:messages:claude-sonnet-4-6
  - anthropic:messages:claude-haiku-4-5-20251001
  - openai:chat:gpt-5.4
  - ollama:chat:llama3.3                # 로컬 모델도 같은 표에 올린다 (OLLAMA_BASE_URL 기본 localhost:11434)

defaultTest:
  assert:
    - type: cost
      threshold: 0.005                  # 호출당 0.5센트 이하
    - type: latency
      threshold: 4000                   # 4초 이하

tests: file://tests/golden.csv

설정 파일을 안 고치고 명령줄에서 모델만 바꿔 볼 수도 있다.

promptfoo eval -r anthropic:messages:claude-opus-5 openai:chat:gpt-5.4

모델별 옵션(temperature, max_tokens 등)은 id 대신 객체로 적는다.

providers:
  - id: anthropic:messages:claude-sonnet-4-6
    config:
      temperature: 0
      max_tokens: 1024

07활용 C - RAG 평가사내 문서 봇

RAG는 두 단계(검색, 생성)라 따로 재야 한다. 검색이 맞는 문서를 가져왔는지와 생성이 그 문서에만 근거했는지는 다른 실패다.

문맥을 넘기는 세 가지 방법

  • vars.context에 직접 문자열로 - 생성 단계만 고립 테스트할 때.
  • context: file://docs/policy.md - 문서 파일을 그대로 문맥으로.
  • contextTransform: 'output.context' - 자체 파이프라인이 응답에 문맥을 함께 돌려줄 때 거기서 추출.

생성 단계 검사

prompts:
  - "다음 문서만 근거로 답하세요.\n문서: {{context}}\n질문: {{query}}"

providers:
  - anthropic:messages:claude-sonnet-4-6

tests:
  - vars:
      query: "출장비 승인은 누가 하나요?"
      context: file://docs/expense-policy.md
    assert:
      - type: context-faithfulness     # 문서에 없는 말을 지어내지 않았는가
        threshold: 0.7
      - type: answer-relevance         # 질문에 직접 답했는가
        threshold: 0.9
      - type: factuality               # 기준 답과 사실이 일치하는가
        value: "출장비 승인권자는 부서장이다"

검색 단계 검사

검색 함수를 Python 프로바이더로 감싸 "어떤 문서를 가져왔는지"만 본다.

# retrieve.py
def call_api(query, options, context):
    docs = vectorstore.query(query, k=3)
    return {"output": "\n".join(d.name for d in docs)}

# promptfooconfig.yaml
providers:
  - file://retrieve.py
tests:
  - vars: { query: "출장비 승인은 누가 하나요?" }
    assert:
      - type: contains-all
        value: ["expense-policy.md"]      # 이 문서가 검색돼야 한다
      - type: context-recall
        value: "승인권자는 부서장"
        threshold: 0.8

08활용 D - 배포된 API·자체 앱 테스트엔드투엔드

모델을 직접 부르는 대신 우리 서비스의 엔드포인트를 프로바이더로 잡으면, 프롬프트·검색·후처리가 합쳐진 실제 동작을 채점한다.

HTTP 프로바이더

providers:
  - id: https://api.example.com/v1/chat
    config:
      method: POST
      headers:
        Content-Type: application/json
        Authorization: "Bearer {{env.SERVICE_TOKEN}}"   # 비밀은 환경 변수로
      body:
        message: "{{prompt}}"
        user_id: "{{user_id}}"                          # tests.vars 도 그대로 쓸 수 있다
      transformResponse: "json.reply"                   # 응답 JSON에서 채점할 문자열 추출

tests:
  - vars: { user_id: "u-001" }
    assert:
      - type: llm-rubric
        value: "환불 규정을 안내하고 규정 외 약속은 하지 않는다"

다회 대화가 필요한 API는 sessionParser로 응답 헤더나 본문에서 세션 ID를 뽑아 다음 요청 헤더에 넣는다.

Python·JavaScript 프로바이더

HTTP로 노출되지 않은 내부 함수는 스크립트로 감싼다. call_api(prompt, options, context)가 {"output": 문자열}을 돌려주면 된다.

# my_app.py
from app.chat import answer

def call_api(prompt, options, context):
    reply = answer(prompt, user=context["vars"].get("user_id"))
    return {"output": reply}

# promptfooconfig.yaml
providers:
  - file://my_app.py

09활용 E - 레드팀(취약점 스캔)배포 전 점검

탈옥, 프롬프트 인젝션, 개인정보 유출, 유해 콘텐츠, 환각 등 50종 이상의 공격을 자동 생성해 우리 앱에 쏘고 어디가 뚫렸는지 보고서로 만든다. 공격 생성에는 OpenAI 키를 쓰는 것이 권장된다.

  1. 대상과 목적 설정 - 웹 UI 마법사가 앱 설명(purpose)과 타깃(HTTP·모델·스크립트)을 물어 설정을 만든다. UI 없이 하려면 --no-gui. 
    promptfoo redteam setup
# 또는
promptfoo redteam init --no-gui
  2. 실행 - 플러그인(취약점 종류)마다 테스트를 생성하고 전략(공격 기법)을 씌워 호출한다. 
    promptfoo redteam run
  3. 보고서 - 취약점 종류별 통과율과 실제 뚫린 대화를 본다. 
    promptfoo redteam report

설정 예

description: 상담 봇 레드팀
targets:
  - id: https://api.example.com/v1/chat
    label: cs-bot-staging
    config:
      method: POST
      body: { message: "{{prompt}}" }
      transformResponse: "json.reply"

redteam:
  purpose: "가전 제품 고객 상담. 사용자는 일반 고객. 환불·배송·AS 문의에만 답한다."
  numTests: 5                        # 플러그인당 생성할 공격 수
  plugins:                         # 무엇을 노리나 (취약점 종류)
    - harmful                        # 유해 콘텐츠 유도 (harmful:hate 등 세부 지정 가능)
    - pii                            # 개인정보 유출 (pii:direct, pii:session 등)
    - hallucination
    - excessive-agency               # 권한 밖 행동 유도
    - id: policy                     # 우리 규정 위반 - 규정 문장을 직접 적는다
      config:
        policy: "환불·배송·AS 외 주제에 답하지 않는다. 금액 보상을 약속하지 않는다."
  strategies:                        # 어떻게 공격하나 (기법)
    - jailbreak
    - prompt-injection
    - crescendo                      # 여러 턴에 걸쳐 서서히 압박
스테이징에만 쏜다

레드팀은 실제로 유해한 요청을 보낸다. 운영 엔드포인트가 아니라 스테이징에, 그리고 로그·알림이 오작동하지 않게 팀에 알리고 돌린다.

10CI 연동 - 종료 코드로 배포 게이트팀 도입

promptfoo eval은 실패 케이스가 하나라도 있으면 종료 코드 100을 돌려준다. CI는 0이 아닌 종료 코드를 실패로 보므로, 명령 한 줄이 그대로 배포 게이트가 된다. 코드를 바꾸려면 환경 변수 PROMPTFOO_FAILED_TEST_EXIT_CODE.

방법 1 - 아무 CI에서나 되는 최소 구성

# .github/workflows/prompt-eval.yml
name: prompt-eval
on:
  pull_request:
    paths: ["prompts/**", "evals/**"]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "24" }
      - run: npx promptfoo@latest eval -c evals/promptfooconfig.yaml -o evals/result.json
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: promptfoo-result, path: evals/result.json }

실패하면 이 잡이 빨간불이 되고 머지가 막힌다. GitLab CI·Jenkins도 같은 한 줄이면 된다.

방법 2 - 공식 GitHub Action (PR에 비교 링크 코멘트)

      - uses: actions/cache@v4
        with:
          path: ~/.cache/promptfoo
          key: ${{ runner.os }}-promptfoo-v1
      - uses: promptfoo/promptfoo-action@v1
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          config: evals/promptfooconfig.yaml
          prompts: "prompts/**/*.txt"
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}

PR을 열면 변경 전후 결과를 나란히 볼 수 있는 링크가 코멘트로 달린다. permissions: pull-requests: write가 필요하다.

공유 링크 주의

--share는 결과를 promptfoo 클라우드에 올려 URL을 만든다. 프롬프트와 출력이 외부로 나가므로 사내 데이터가 섞인 평가에는 쓰지 않는다. 자체 서버(promptfoo view)나 JSON 산출물로 대체한다.

11Claude Code 하네스에 연결 - Stop 훅 게이트발표 자료 71~72p

발표 자료의 "거짓 완료를 물리적으로 막는다"는 Stop 훅이 종료 전에 점수 파일을 확인하는 구조였다. 점수 파일을 손으로 만들 필요 없이, Stop 훅에서 promptfoo를 돌리고 그 종료 코드를 그대로 쓰면 된다. promptfoo가 100을 돌려주면 훅은 2를 돌려주고, Claude Code는 완료 선언을 거부하고 작업을 이어 간다.

# .claude/settings.json
"Stop": [{ "hooks": [{ "type": "command",
  "command": "bash .claude/hooks/eval-gate.sh" }] }]

# .claude/hooks/eval-gate.sh
n=$(cat .eval/attempts 2>/dev/null || echo 0)
if [ "$n" -ge 5 ]; then
  echo "retry cap reached - escalate to human" >&2; exit 0
fi
if npx promptfoo@latest eval -c evals/promptfooconfig.yaml --no-cache -o .eval/result.json; then
  rm -f .eval/attempts; exit 0                      # 전 케이스 통과 - 종료 허용
else
  echo $((n+1)) > .eval/attempts
  echo "promptfoo eval failed - see .eval/result.json, fix and retry" >&2
  exit 2                                            # 미달 또는 실행 실패 - 종료 거부 (fail-closed)
fi
  • 실행 자체가 실패해도(설정 오류, 키 없음) else로 떨어져 차단된다. "모르면 막는다"가 자동으로 지켜진다.
  • 재진입 상한(5회)은 훅 입력의 stop_hook_active만으로는 셀 수 없어 파일 카운터로 센다.
  • Claude가 stderr로 받는 문장은 "왜 막혔는지"를 담아야 다음 시도가 나아진다. 결과 JSON 경로를 함께 준다.

  assert:
    - { type: cost, threshold: 0.01, weight: 0, metric: cost }      # 참고 지표로만 기록

뷰어에서 "Haiku가 통과한 케이스 집합"이 Sonnet과 같으면 그 유형은 Haiku로 라우팅해도 된다는 근거가 된다.

13운영 팁과 함정겪기 전에

함정증상대처
캐시 때문에 안 바뀐 것처럼 보임모델 설정을 바꿨는데 결과가 그대로프롬프트·입력이 같으면 캐시 적중. --no-cache 또는 promptfoo cache clear
AI 채점이 흔들림같은 출력이 어제는 통과, 오늘은 실패기준을 구체 문장으로(수치·조건). 채점자 temperature 0. 중요한 건 코드형 단언으로 내린다
자기 채점 편향합격률이 비현실적으로 높음구현 모델과 채점 모델 분리. 골든셋 기대 답은 사람이 검수
케이스가 너무 쉬움항상 100%라 회귀를 못 잡음실제 실패 사례를 골든셋으로 승격. 경계 사례·적대 사례를 20% 이상 섞는다
비용 폭증모델 3개 × 케이스 200 × 반복 3--filter-pattern으로 부분 실행, --max-concurrency로 속도 제어, 캐시 활용
비밀 키 유출설정 파일에 키를 적어 커밋항상 환경 변수 {{env.NAME}}. 설정 파일은 공개돼도 안전해야 한다
공유 링크로 데이터 유출--share URL이 외부에 노출사내 데이터 평가엔 --share 금지. JSON·HTML 산출물로 공유
Windows에서 npx 오류실행 정책 또는 경로 문제PowerShell에서 npx.cmd promptfoo@latest ..., 또는 전역 설치

도입 순서 제안

  1. 가장 자주 깨지는 기능 하나를 고른다. 케이스 5개, 코드형 단언만으로 시작한다. 오늘 안에 끝난다.
  2. 일주일 운영하며 실패 사례를 골든셋에 추가한다. 20개가 되면 CSV로 옮긴다.
  3. 태도·품질 기준을 llm-rubric으로 추가하되 채점 모델을 분리한다.
  4. PR마다 CI에서 돌린다. 실패하면 머지가 막히는 상태를 만든다.
  5. 배포 전 스테이징에 레드팀을 한 번 돌리고, 뚫린 유형을 골든셋에 넣는다.
