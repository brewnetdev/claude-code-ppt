## 0. 용어 사전 — 풀네임 · 한글 발음 · 뜻 · 언제 쓰나

> 이 표가 L5의 뼈대다. 발표 전 청중에게 "모르는 약어가 나오면 이 페이지로 돌아오라"고 안내한다.
> 표기: **한글 발음**은 실제 강의장에서 읽는 소리 그대로(문자 나열이 아닌 관용 발음 우선).

### 0.1 요구사항 · 기획 용어

| 용어 | 풀네임(원어) | 한글 발음 | 뜻 | 어떤 경우에 쓰나 |
|---|---|---|---|---|
| **KMS** | Knowledge Management System | 케이엠에스 (지식관리시스템) | 문서·지식을 저장·분류·검색·공유하는 시스템 | markflow가 만드는 결과물. "위키/노션 같은 걸 만든다"의 정식 명칭 |
| **FR** | Functional Requirements | 에프알 (기능 요구사항) | 시스템이 **무엇을** 하는가(로그인·문서 CRUD 등) | 기능 목록을 번호(FR-001~)로 고정할 때 |
| **NFR** | Non-Functional Requirements | 엔에프알 (비기능 요구사항) | **어떻게** 잘 동작하는가 — 성능·보안·확장성 등 품질 속성 | "응답 300ms 이하", "XSS 방어"처럼 품질 기준을 못 박을 때 |
| **MVP** | Minimum Viable Product | 엠브이피 (최소 기능 제품) | 첫 출시에 반드시 필요한 최소 기능 묶음 | "이번엔 어디까지, 무엇은 제외"를 가를 때 |
| **US** | User Story | 유저 스토리 (사용자 스토리) | 역할·행동·가치를 한 문장으로 쓴 요구 표현 | FR을 "누가·왜"까지 담아 사용자 관점으로 옮길 때 |
| **Connextra** | Connextra (사)의 사용자 스토리 표준 템플릿 | 커넥스트라 | `As a [역할], I want [기능], so that [가치]` 문장 포맷 | 사용자 스토리를 표준 형식으로 통일할 때 (출처: agilealliance.org) |
| **유스케이스** | Use Case | 유스케이스 | 사용자–시스템 상호작용 시나리오(정상/예외 흐름) | 기능 하나가 실제로 어떻게 흘러가는지 단계로 적을 때 (UC-001~) |

### 0.2 문서 · 명세 용어

| 용어 | 풀네임(원어) | 한글 발음 | 뜻 | 어떤 경우에 쓰나 |
|---|---|---|---|---|
| **PRD** | Product Requirements Document | 피알디 (제품 요구사항 문서) | 제품이 **무엇을** 해야 하는지 — 기능·시나리오·MVP 범위 | 기획 단계에서 "무엇을 만드는가"를 한 문서로 확정할 때 |
| **TRD** | Technical Requirements Document | 티알디 (기술 요구사항 문서) | **어떻게** 구현할지 — 아키텍처·데이터 흐름·보안 | 아키텍처·계층 경계·배포 전략을 못 박을 때 |
| **SSOT** | Single Source of Truth | 에스에스오티 (단일 진실 공급원) | 모든 결정이 참조하는 **하나의** 기준 문서 | FR·NFR·US를 REQUIREMENTS.md 한 곳에 통합할 때 |
| **SDD** | Specification-Driven Development | 에스디디 (명세 주도 개발) | 명세를 기준으로 AI·사람이 구현·검증하는 방식 | AI가 "합리적이지만 틀린 가정"을 못 하게 명세로 묶을 때 |
| **Spec Drift** | Specification Drift | 스펙 드리프트 | 코드와 명세가 점점 어긋나 쌓이는 현상 | 요구가 바뀌는데 문서를 안 고쳐 생기는 불일치를 경고할 때 |

### 0.3 데이터 · API 용어

| 용어 | 풀네임(원어) | 한글 발음 | 뜻 | 어떤 경우에 쓰나 |
|---|---|---|---|---|
| **ERD** | Entity-Relationship Diagram | 이알디 (개체-관계 다이어그램) | DB 스키마를 개체·관계로 그린 설계도 | 14개 테이블 구조를 그림으로 합의할 때 |
| **ORM** | Object-Relational Mapping | 오알엠 (객체-관계 매핑) | 객체 코드로 DB를 다루는 계층(SQL 자동 생성) | 코드에서 SQL을 직접 쓰지 않고 타입 안전하게 DB를 다룰 때 |
| **Drizzle ORM** | Drizzle ORM | 드리즐 오알엠 | TypeScript 타입 안전 SQL-like ORM | 서버리스·코드 생성 없는 가벼운 ORM이 필요할 때(markflow 선택) |
| **Closure Table** | Closure Table (Adjacency 대안) | 클로저 테이블 | **계층(트리) 구조를 평면 테이블로** 저장하는 패턴 | 카테고리 폴더처럼 무한 깊이 트리를 SQL로 빠르게 조회할 때 |
| **멀티테넌시** | Multi-tenancy | 멀티테넌시 (멀티테넌트) | 한 인스턴스로 여러 팀·회사를 **격리** 수용 | 워크스페이스별로 데이터를 분리(팀별 DB 분리)할 때 |
| **REST** | Representational State Transfer | 레스트 | HTTP 동사 + 자원 URL로 API를 설계하는 방식 | 엔드포인트 계약(GET/POST/PATCH/DELETE)을 정할 때 |
| **Contract** | API Contract | 컨트랙트 (API 계약) | 요청/응답 형식의 사전 합의 | 프론트·백엔드가 필드명을 임의로 못 바꾸게 못 박을 때 |
| **CRUD** | Create · Read · Update · Delete | 크러드 | 데이터 생성·조회·수정·삭제 기본 4연산 | "이 자원에 대해 4연산을 다 지원한다"를 말할 때 |
| **CORS** | Cross-Origin Resource Sharing | 코스 (교차 출처 리소스 공유) | 다른 출처(도메인) 간 요청을 허용하는 브라우저 정책 | 프론트·API 도메인이 다를 때 필요. markflow는 same-origin이라 **불필요** |
| **Optimistic Update** | Optimistic Update | 옵티미스틱 업데이트 (낙관적 업데이트) | 서버 응답 전에 화면을 먼저 갱신, 실패 시 롤백 | 저장 지연 없이 반응성을 높이되 충돌 시 되돌릴 때 |
| **Zod** | Zod (schema validation) | 조드 | 런타임 입력 검증 스키마 라이브러리 | Route Handler에서 요청 바디를 서버 진입 시점에 검증할 때 |

### 0.4 인증 · 보안 용어

| 용어 | 풀네임(원어) | 한글 발음 | 뜻 | 어떤 경우에 쓰나 |
|---|---|---|---|---|
| **JWT** | JSON Web Token | 제이더블유티 (제이오티) | 서명된 토큰으로 서버 세션 없이(무상태) 인증 | 로그인 후 Access/Refresh 토큰으로 보호 자원에 접근할 때 |

| **XSS** | Cross-Site Scripting | 엑스에스에스 (교차 사이트 스크립팅) | 악성 스크립트를 주입해 남의 브라우저에서 실행 | 마크다운/댓글처럼 사용자 입력을 HTML로 렌더할 때 최우선 방어 |
| **Stored XSS** | Stored(Persistent) XSS | 스토어드 엑스에스에스 (저장형 XSS) | 서버에 저장된 악성 코드가 열람자 모두에게 실행 | 저장된 문서·댓글이 뇌관이 되는 최악 시나리오를 설명할 때 |
| **Defense in Depth** | Defense in Depth | 디펜스 인 뎁스 (다층 방어) | 여러 방어선을 중첩해 하나 뚫려도 막는 전략 | sanitize·CSP·프로토콜 차단을 겹쳐 쌓을 때 |
| **bcrypt** | bcrypt (password hashing) | 비크립트 | 느린 해시로 토큰/비밀번호를 단방향 저장 | 게스트 토큰·비밀번호를 DB에 평문으로 두지 않을 때 |

## 1. 오프닝 (슬라이드 1~3)

### 슬라이드 1 — 용어 참조 (LEVEL 5 · GLOSSARY)
- **[화면]** L5 전체 약어 한 장(KMS·FR·NFR·SSOT·RBAC·CORS·Closure Table…).
- **[멘트]** "L5는 약어가 많습니다. RBAC, CORS, Closure Table 같은 용어가 계속 나오는데, 모르면 이 페이지로 돌아오세요. 지금은 딱 하나만 — L5는 **markflow라는 마크다운 KMS**를 기획부터 배포까지 만들면서, **명세를 기준으로 AI와 협업하는 법(SDD)**을 배우는 챕터입니다."

### 슬라이드 2 — Level 5 목차 (CONTENTS)
- **[화면]** 5.1~5.7 일곱 파트.
- **[멘트]** "흐름은 기획(5.1) → 문서(5.2) → 명세·DB 설계(5.3) → SDD 워크플로 GSD(5.4) → 세션 연속성(5.5) → 디버깅·리팩토링(5.6) → 프론트엔드 고도화(5.7)입니다. 5.3이 별 두 개(⭐⭐)인 이유는 골격이 틀리면 뒤가 전부 어긋나기 때문입니다."

## 5. PART 04 — 5.4 SDD 워크플로 (GSD) (슬라이드 24~28)

- **[멘트]** "**GSD(지에스디, Get Shit Done)**는 메타프롬프팅 + 컨텍스트 분리 + SDD를 통합한 Claude Code 시스템입니다. `.planning/` 아래 PROJECT·REQUIREMENTS·ROADMAP·STATE·HANDOFF를 두고 **Phase(페이즈) 단위로 컨텍스트를 분리**해 Context Rot 없이 완성해요. 설치는 `--dangerously-skip-permissions`로 **초기 1회만** — 이후는 일반 모드입니다. 다만 작업이 꼼꼼한 만큼 토큰을 많이 써서 Pro 요금제엔 부담일 수 있어요."
