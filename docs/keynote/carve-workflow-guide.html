carve-harness — 사용 가이드

carve-harness는 bash 훅과 마크다운으로만 구성된 제로 의존성 하네스다. 코딩 에이전트의 규칙 위반은 설득이 아니라 PreToolUse·Stop 훅의 exit 2로 막고, 완료 선언은 주장이 아니라 verify-loop 채점과 골든셋 평가로 검증한다. 프로젝트 루트에 설치하면 즉시 동작한다.

이 가이드의 이전 버전은 /carve-workflow 스킬과 7단계 절차 루프·8요소 출력 형식을 다뤘다. carve-harness v0.10.1에는 이 스킬도, 7단계 루프도, 8요소 형식도, "Fablize" 같은 자연어 트리거도, sprint-contract.md·evaluation-criteria.md도, squad-* 에이전트도 존재하지 않는다. 저장소 전체를 검색해도 관련 문구는 한 건도 나오지 않는다.

대체 대응은 다음과 같다.

  • 검증 루프 → /verify-loop (+ checklist-loop 스킬)
  • 완료 게이트 → eval-score.sh의 G1·G2·G3 거부권
  • 계획·검증 → /plan · /verify
  • 에이전트 → Squad 9종이 아니라 7종 (evaluator · fable 4종 · pr-test-analyzer · security-reviewer)

ABOUTcarve-harness 한눈에

carve-harness는 bash 훅과 마크다운으로만 구성된 하네스다. package.json 설명을 그대로 옮기면 "Bash-hook + markdown harness — npm scripts wrap the shell test suites (zero dependencies)"이며, TypeScript가 아니고 Node 버전 요구도 없고 빌드 단계도 없다. 전제는 하나다 - 코딩 에이전트의 규칙 위반은 설득이 아니라 훅의 exit 2로 막는다. 프로젝트 루트에 내려받으면 바로 동작한다.

"필요한 것만 남기고, 나머지는 깎아낸다."

PART 1설치와 시작 순서

설치

cd /path/to/your-project
curl -fsSL https://raw.githubusercontent.com/claude-code-expert/carve-harness/main/install.sh | bash

설치 시작 시 다음 둘 중 하나를 묻는다.

  • [1] 프로젝트 분석 후 맞춤 하네스 구축 (권장) - 전체 설치 후 세션에서 /carve-harness-create를 실행해 맞지 않는 규칙·에이전트·스킬을 prune한다.
  • [2] 수동 컴포넌트 선택

구성 선택 TUI는 ↑↓/jk로 이동, 스페이스로 토글, 1~5로 섹션 점프, a로 전체 토글, 엔터로 설치한다. 기본값은 전체 선택이다. 비대화형 설치는 환경변수로 처리한다. 

HARNESS_COMPONENTS=md,hooks bash install.sh

기존 파일은 건드리지 않고 SKIP으로 보고한다. 설치된 목록은 .claude/harness-manifest.txt에 남는다.

예외 - settings.json은 스킵하지 않는다

.claude/settings.json만은 스킵이 아니라 jq로 병합한다 - 훅 6이벤트와 LSP·플러그인 선언을 등록하며 멱등이다. 스킵하면 훅이 등록되지 않아 전 게이트가 무력화되기 때문이다.

언어팩은 HARNESS_PACKS=auto|none|all|typescript,python로 지정한다(미지정 시 auto). 설치 후에는 bash install.sh pack list|add <name>|remove <name>로 조정한다.

오프라인 설치는 HARNESS_SRC_DIR=/path/to/harness bash /path/to/harness/install.sh. 소스 저장소를 바꾸려면 HARNESS_REPO=<owner>/<repo> · HARNESS_REF=<branch|tag>를 쓴다. 단 2026-09-06 개정에서 README의 오프라인 설치 절이 삭제됐다 - 기능은 install.sh에 그대로 남아 동작하지만(HARNESS_SRC_DIR 참조 6곳), 상류 문서에는 더 이상 근거가 없으므로 향후 제거될 수 있다.

초기 설정(선택)은 bash install.sh setup - git init · jq PATH 확보 · LICENSE 생성 · 보호 경로 추가 · 도메인 규칙 수집 · 스택 감지 리포트를 한 번에 처리한다.

설치가 끝나면 /harness-audit가 자동 실행된다.

업데이트는 curl … | bash -s -- update 또는 bash install.sh update. 롤백은 bash install.sh rollback(백업은 소비되므로 연속 실행하면 한 단계씩 과거로 돌아간다). 현재 버전 확인은 cat .claude/harness-version. 제거는 bash uninstall.sh(드라이런) 또는 bash uninstall.sh --yes.

PART 4검증 3층

이 도구의 핵심이다. 세 층은 서로 다른 것을 채점한다.

  • verify-loop - 태스크 하나의 스펙 정합성을 항목 단위로 채점
  • eval-score - 지금 이 순간의 빌드 건강도를 결정적으로 채점
  • 골든셋 평가 - 고정 케이스 집합의 품질을 시간축으로 추적

1) verify-loop - 스펙 정합성 채점

"구현했다"는 주장(claim)을 하나씩 실제 코드와 대조해 0~100점으로 채점하고, 95점 미만 항목만 gap을 되먹여 다시 고치는 루프다. stop-verify가 빌드·테스트 통과 여부만 보는 것과 달리, 스펙의 각 요구가 실제로 구현됐는지를 항목 단위로 본다.

채점은 교차검증이다. 코드를 짠 빌더가 아니라 독립 evaluator가 항목마다 다음을 수행한다.

  1. 코드 대조 - claim이 acceptance를 문자 그대로 충족하는지 Read/Grep으로 확인, 주장을 믿지 않는다
  2. 테스트 실행 - 통과/실패/스킵/미수집 구분, 명령 성공 ≠ 결과 정확
  3. 감점·근거 - 파일:라인과 테스트 원문을 evidence로
  4. gap - 95 미만이면 "무엇을 어떻게"를 구체로

생성자와 채점자를 분리해 Self-Eval Blindspot을 막는다.

5단계 (carve-verify-loop 워크플로):

P1 Checklist  목표 → 항목 분해 (claim·acceptance·owns) → specs/checklist.json
P2 Build      항목별 빌더 (worktree 격리)
P3 Score      항목별 evaluator → 코드 대조 + 테스트 실행 → 5축 루브릭(exists·match·test·contract·no_regress, 합 100) + gap·evidence
P4 Loop       score<95 항목만 gap 되먹여 P2로 (항목당 최대 3회, 외곽 8회)
P5 Verify     전 항목 95↑ → 통합 최종 판정

사용: /verify-loop 주문 취소 API 구현(목표만 주면 항목 자동 분해 3~7개). 항목을 직접 지정하려면 워크플로로 - 발화에 carve-verify-loop 실행 또는 ultracode + {goal, threshold, tasks[]}.

효과: 미달·미채점 항목이 남으면 checklist-gate가 완료 선언을 exit 2로 차단한다. 재작업은 실패 항목만 외과적으로 고친다. checklist.json이 없으면 게이트는 무동작이라 일반 작업은 방해받지 않는다.

불변식 (checklist-loop 스킬)
  • 생성자와 채점자는 절대 같은 에이전트가 아니다
  • 주장을 믿지 않는다
  • 완료 = 모든 항목 ≥ 임계(기본 95)
  • 에이전트 간 통신은 파일 기반(specs/checklist.json이 단일 진실원)

2) eval-score - 빌드 건강도 채점표

bash .claude/hooks/eval-score.sh. LLM 없이 결정적으로 채점한다.

항목배점
G1 빌드25
G2 테스트25

lint10
regression10
coverage5

G1~G3은 거부권을 가진다 - 하나라도 0점이면 총점과 무관하게 verdict: FAIL. 거부권이 없으면 total/max >= 0.9일 때 PASS. 못 잰 항목은 skipped로 명시되고 분모에서 빠진다(조용한 통과가 아니다). 스택을 하나도 감지하지 못하면 verdict: "unable", exit 1로 fail-closed. 산출물은 specs/SCORE.json. 다중 스택은 게이트는 AND, 총점은 min을 취한다.

이 G1·G2·G3 거부권과 90% 통과선은 구 문서에도 있던 개념으로, 현재도 유효하다.

3) 골든셋 평가 (carve-eval)

verify-loop가 태스크당 완성도를 본다면, 이건 고정 케이스 집합의 품질을 시간축으로 추적한다. 

Validate  carve-validate.sh 프리플라이트 - 설정 오류를 런 전에 분리(에이전트 0회). 실패 시 런을 시작하지 않는다(비용 보호)
Load      specs/goldenset/*.json → 케이스(입력·assert·k·version)
Run       케이스별 k회 실행 → 텍스트 assert + 상태 assert + llm-rubric 채점

          → 케이스 version이 직전 run과 다르면 [VERSION CHANGED]

케이스 자동 확정을 막아둔 이유

케이스 자동 확정은 의도적으로 막아뒀다 - 에이전트가 혼자 만든 골든셋은 자기가 이미 통과하는 것만 담아(자기강화) 지표를 무의미하게 만든다. 크리티컬 경로·실패 소재·엄격도는 사람이 정한다.

이 저장소 자신의 골든셋 20건이 작성 예시다(가드 준수 5 · 작업 품질 5 · 고난도 5 · 하네스 자체 5). 케이스는 양방향 검증이다 - 작업 전에는 실패해야 하고(--red), 정답 상태에서는 통과해야 한다.

CI 강제는 옵트인이다. eval-gate.sh --mode report|block이 추이 파일만 읽어 결정적으로 판정한다(LLM 없음): unable → stale → suspicious → regressed → ok. 차단 모드는 골든셋을 유지할 사람이 있을 때만 권한다.

PART 7한계

적대적 감사에서 실제로 뚫린 지점만 싣는다.

실제로 뚫린 것
  • 훅 차단은 Claude Code 전용 - 타 에이전트는 pre-commit이 커밋 시점 차단.
  • Bash 쓰기 가드는 명령 표면만 본다. 변수 간접(F=.env; echo x > $F)·인터프리터 경유(python3 -c "open('.env','w')")는 미탐(pre-commit이 2차 차단). 리다이렉트·tee·cp/mv·sed -i·rm/touch는 차단됨.
  • 시크릿 스캔은 리터럴 매칭이다. base64 인코딩·문자열 분할 조립("sk-"+"...")은 미탐 - 사람이 리뷰해야 한다.
  • 위험 명령 차단은 명령 위치 기준이다. env/sudo/VAR= 접두는 커버하지만 셸 alias·함수로 감싸면 미탐, curl -o file && bash file도 미탐.
  • Stop 게이트 스택은 Java·Node/TS·Python·Go·Rust·bash. 그 외는 미검증 통과. 각 스택은 툴체인이 설치돼 있을 때만 문다.
  • 게이트 자기보호(GUARD-07)는 설치본에서만 활성(하네스 소스 저장소는 자기 훅을 편집해야 하므로 예외).
  • 검증 루프 게이트는 checklist.json 삭제·threshold 하향은 막지만 채점 내용 자체가 거짓이면 막지 못한다(evaluator 분리로 완화).

무엇을 보장하고 무엇을 보장하지 않는가

상류 저장소의 자기평가(specs/fitness-assessment.md, 2026-09-06)가 이 경계를 명시한다. 핵심 구분은 이것이다 - 이 하네스는 과정 품질(process floor)을 강제하지 도메인 정합성(correctness)을 보장하지 않는다.

실패 1건의 원인

유일한 실패는 core.hooksPath unset — run install.sh (AUDIT-04)였다. 이는 install.sh를 돌리지 않은 맨 클론이라 당연히 나는 결과이며 제품 결함이 아니다. 테스트 실패 1건도 같은 원인(live baseline exit 0)이다.
